## 2. 需求小卡

要解决的问题：把用户输入的学习主题或文本，变成可以立即练习并复盘的一组学习关卡。

完成后用户能够：输入主题 → 生成题目 → 选择并提交答案 → 阅读即时讲解 → 完成报告 → 从本机题库或“我的”继续学习与复盘。

最重要的五项预期：

1. 正式前端使用 Taro，产出可导入微信开发者工具的小程序工程；Python 后端真实调用 AI。
2. 页面布局、颜色、文案和交互遵循用户提供的原型，保留五页与三栏导航。
3. 每轮默认 5 题，包含单选、多选、判断；提交后立即反馈，重复提交不重复加分。
4. 报告统计与真实作答一致；生成失败可以重试，输入、成绩与进度不会因此丢失。
5. 后端所有业务功能按 TDD 开发，交付测试结果、启动说明及可复现的验收步骤。

第一个样品：真实出题接口配合原型样式的输入页及答题页，展示“输入 RAG 主题 → 生成 5 题 → 提交一题 → 查看讲解与 XP”。样品中真实 AI 数据、测试用固定数据会明确区分。展示后等待用户确认还原效果和答题体验，再大幅展开其余页面；不依赖该反馈的后端 TDD 可继续。

## 4. 技术文档核查

已通过 Context7 完成 Taro、LangChain、FastAPI 的库 ID 解析并检索文档，同时直接核对 DeepSeek 和 LangChain 当前官方页面。

- [LangChain ChatDeepSeek](https://docs.langchain.com/oss/python/integrations/chat/deepseek)
- [DeepSeek 当前 API 入口与模型名称](https://api-docs.deepseek.com/)
- [DeepSeek JSON 输出](https://api-docs.deepseek.com/guides/json_mode/)
- [DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)

核查结论和实施约束：

1. 不直接把 with_structured_output 的默认行为等同于 DeepSeek 支持的协议。明确指定经验证的输出方式，Prompt 描述 JSON 字段，服务端再次校验结构和业务约束。
2. DeepSeek 官方 JSON 输出要求 response_format 为 json_object，Prompt 包含 JSON 说明，并提示可能出现空输出或截断；这些情况需要有界重试及明确错误响应。
3. 当前模型默认开启思考模式。首轮推荐显式关闭以控制耗时；参数由最新官方文档及适配器实际行为共同验证，不直接照搬旧方案里的 top_p、temperature 组合。
4. LangChain 的部分索引示例仍使用旧模型名；模型名称以 DeepSeek 当前官方资料为准，适配器能力以所安装版本及真实调用结果为准。
5. 开始编码前继续查询 Pydantic v2、pydantic-settings、pytest 及所用 Taro API 的官方用法，检查包的兼容版本并锁定依赖。React 18、Taro 4.x 为方案基线，若出现必须变更的兼容问题先告知用户确认。

计划新增的工程范围：

| 路径 | 职责 |

| backend/app/api/v1/routes/ | 健康检查、生成题库、生成报告三个接口 |
| backend/app/models/、backend/app/services/ | 数据契约、出题服务、评分服务、报告服务 |

| backend/app/core/、backend/app/utils/ | 配置、错误映射、日志、文本处理、内容规则与基础限流 |
| backend/tests/、frontend/tests/ | 后端 TDD、前端判题/恢复测试及端到端验证 |
| README.md、backend/.env.example、frontend/.env.example | 本地启动、配置示例、测试方式及验收说明 |

保留方案接口：

- `GET /api/v1/health`。
- `POST /api/v1/quiz/generate`：user_input、question_count、difficulty → 标准化 Quiz。
- `POST /api/v1/report/generate`：quiz_id、topic、questions、answer_records → 统计及结构化 Report。
- 响应统一为 code、message、data；HTTP 状态码与业务错误对应，校验失败也遵循统一格式。

前端逐题即时判题；报告服务根据题目答案和 selected_answers 重新计算结果，不直接信任客户端 is_correct。后端首轮无状态，接收客户端持有的完整题库用于个人学习复盘。

题量 API 支持 3—5 题，首页按原型固定生成 5 题；3/4/5 题分别采用 1/2/3 道单选、1 道多选、1 道判断。单选和多选均提供 A—D，判断为 A/B。多选必须集合完全一致才算答对。

报告中的正确率、正确题数、XP、掌握与薄弱知识点由评分服务确定；AI 负责知识总结和学习建议。同一知识点存在错题时优先归入待巩固，全部答对不虚构薄弱点。平均正确率按已完成总题数加权，累计 XP 包含未完成关卡已获得的 XP。

正式使用首次打开显示原型提供的空态；示例题库仅用于测试或明确标注的演示。答题完成状态与报告生成状态分开保存，报告失败可以重试而不要求重答。

## 6. 确认后的具体执行步骤

1. **固定范围、样式和验收清单。** 根据用户对 C1—C4 的答复更新本文件，记录最终技术适配方案；建立需求、原型状态与实现测试的对应清单。
2. **准备可运行的前后端基础。** 查询并锁定兼容依赖，建立 Taro + React + TypeScript 和 FastAPI + Python 3.11 工程，提供脱敏配置模板。后端健康检查、参数校验和统一错误处理先写失败测试，再实现。
3. **TDD 完成真实出题能力。** 先覆盖输入、题型 Schema、输出约束、模型参数、空结果、非法 JSON、超时、限流及重试；再实现 Prompt、模型工厂和生成接口。模型依赖可替换，自动化测试不依赖真实 API Key。
4. **交付首个可操作样品。** 严格迁移原型输入、加载、失败、答题及反馈样式；接入真实出题。展示一题作答的完整过程，并等待用户确认外观、提交方式和讲解体验。
5. **TDD 完成评分与报告。** 先覆盖三种题型、完整作答约束、篡改 is_correct、重复/遗漏记录、0 分与满分、知识点聚合、报告重试和统计不一致，再实现报告链和接口，接入报告页面。
6. **补齐题库、“我的”和本机恢复。** 按原型实现搜索筛选、开始/继续学习、返回来源、最近报告、统计和空态。覆盖关闭重开、退出恢复、缓存损坏、存储失败、报告失败后恢复与重试。
7. **完整联调及视觉核对。** 执行后端测试与覆盖率、前端逻辑测试与类型检查、小程序构建；用可用浏览器对 H5 同源页面与原型逐页截图核对五页及 21 种状态，并在微信开发者工具核对小程序特有的胶囊、安全区、导航和存储。H5 仅作为同一 Taro 工程的预览验证入口，小程序是主交付物。
8. **真实模型验收与交付。** 用户在本机配置 API Key 后，按方案执行连续 10 次真实出题抽检，并测试不同正确率下的报告变化；提供源码、锁定依赖、环境模板、启动说明、验收表及未验证项目。提交、推送、部署和发布需用户明确要求。

## 7. 后端 TDD 与验收证据

每个后端业务增量执行：写测试 → 运行并确认因缺少对应行为而失败 → 最小实现 → 测试通过 → 整理代码并复测。用进度记录保留失败和通过的命令、结果；不以事后补测试替代 TDD。

| 测试范围 | 必须验证的行为 |
| --- | --- |
| 输入处理 | 空白、2000 字边界、Unicode 字符计数、非法题量/难度、内容规则拒绝、输入长度变化 |
| 题库契约 | 三种题型、唯一题号/选项、答案属于选项、必需解析与知识点、题量和题型配比、未知/缺失字段 |
| 模型调用 | 正确 Prompt 与配置、异步调用、无 Key 错误、空响应、截断、格式错误、超时、429/上游错误、有界重试与最终失败 |
| 评分 | 单选/判断、多选乱序与少选/多选、重复选项、无效答案、遗漏/重复/多余记录、负用时、忽略客户端正确标记、0%/100%/部分答对及 XP |
| 报告 | 三句总结、知识点归类、同知识点有对有错、AI 与计算统计冲突、AI 失败不返回伪造报告、可重试 |
| HTTP 与基础设施 | 三个路由、统一响应、校验与错误状态码、必要的跨域配置、基础限流、配置校验、异常日志不泄漏密钥 |

最终执行 pytest 及分支覆盖率检查，逐项核对业务行为清单与未覆盖分支。覆盖率数值、实际命令、通过数量以运行结果为准。真实 AI 内容质量和微信真机表现独立验收，不能用固定数据测试通过代替。

初次真实联调所需准备：本机配置 DeepSeek API Key；微信开发者工具及可用 AppID/测试条件；真机能够访问的后端地址。密钥不发送到聊天、不提交到仓库。

## 8. 用户验收路径

| 步骤 | 用户操作 | 应该看到什么 |
| --- | --- | --- |
| A1 | 输入空白或超长文本，点击生成 | 原型式就地提示，输入保留，不发无效生成请求 |
| A2 | 输入“我想理解 RAG 和传统搜索的区别” | 加载反馈后进入真实生成的五题关卡 |
| A3 | 逐题选择并提交，故意答错一道、多选题尝试少选 | 立即显示正确答案和完整讲解；多选按集合判定；XP 与答对数量一致 |
| A4 | 答到一半退出，再从题库继续 | 已提交记录、XP 和当前进度保留，不重复加分 |
| A5 | 完成所有题目 | 展示真实正确率、三句总结、待巩固及可展开的报告建议，支持回看本轮题目 |
| A6 | 模拟出题或报告网络失败，再重试 | 输入或已完成成绩保留；报告重试不要求重答 |
| A7 | 到题库搜索筛选，到“我的”查看统计，关闭重开 | 本机记录可恢复，累计与平均统计符合已保存的真实数据 |
| A8 | 对照 prototype 的主要页面和状态 | 页面布局、文字、间距、颜色和交互符合所确认的原型依据；小程序系统区域使用真实平台能力 |

每阶段按“预期 / 当前结果 / 符合、存在差距或待验证 / 证据”报告。最终明确区分助手已完成的测试、待用户体验确认的事项和环境限制。

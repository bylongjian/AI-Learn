## 1. 需求小卡

要解决的问题：为现有学习闭环增加稳定的用户身份、MySQL 云端记录、个人资料和历史回看。

完成后用户能够：登录 → 生成学习关卡 → 按原方式答题 → 保存报告 → 查看个人统计和历史 → 在另一个客户端读取同一账号的云端记录。

最重要的五项预期：

1. 实现微信静默登录和 JWT 鉴权；登录失败时，现有游客学习功能仍可使用。
2. 登录后的题库、完整作答和报告保存在 MySQL；不同账号互相隔离。
3. 首页和“我的”展示真实账号数据，支持修改昵称及查看历史报告。
4. 保持三种题型、提交后反馈、完整讲解、退出续答、报告失败重试和现有 XP 规则。
5. 所有新增及修改的后端功能都先写失败测试，再实现；同时运行真实 MySQL 集成测试与原有回归测试。

第一个可体验样品：明确标注的本地测试登录 → 原型布局的“我的” → 修改昵称 → 重新打开后仍保存。数据库和请求真实运行，只有微信身份来源使用开发专用测试身份。展示后等待用户反馈，再大幅展开其余前端界面；不依赖界面反馈的后端 TDD 可继续。

## 4. 随开发方案一并请用户确认的范围口径

### C1. 界面新增位置

推荐：沿用现有五页、三栏导航、颜色、间距和原型卡片；首页补充简洁的真实昵称/XP 与已完成记录；“我的”保留原统计卡布局，接入头像、昵称、云端统计和分页历史，并提供昵称修改入口。累计答对题数用同一视觉体系的辅助信息呈现。报告页主体沿用原型。

新需求所述首页区域在原型中没有对应图，因此这部分属于“功能没有原型图”的新增范围。新功能采用现有组件样式，首个样品后由用户确认。不会添加金币功能或不存在的“数学/科学未完成”占位卡。

另一种可选方案是严格保留首页所有现有内容，将账号信息和历史全部集中在“我的”和“题库”；这会省去首页布局增量，但不能满足新用户文档的首页展示项。推荐前一种。

### C2. 云端同步与旧游客数据

推荐按新增用户文档的四个批次实现：登录后新生成的完整题库、完成后的作答和报告进入云端，可跨客户端查阅；逐题即时作答和未完成进度继续保存在当前设备，保留现有退出续答能力。

旧游客数据保留在原有本机存储，不自动上传、不直接加入账号累计值；提供返回游客记录的使用路径。不同账号的缓存和进行中请求隔离，避免旧请求把数据写入新账号。

账号云端累计 XP 在完整报告事务成功后结算；答题页即时 XP 不变。云端不可用或报告失败时，本机作答保留并可重试，页面明确说明保存状态。

如果本次还要求“答到第 2 题，换设备从第 3 题继续”，或把所有旧游客记录归入账号，需要额外的逐题同步/迁移接口及冲突规则，超出当前四批次接口，必须先扩展确认后的范围。

### C3. 环境准备

按用户后续补充复用已有 MySQL 8.0.46、默认端口 3306。已建立独立应用库 ai_learn 和测试库 ai_learn_test，各用独立随机密码账号。原 AI Key 保留；密码和 JWT 密钥只写入被忽略的本机配置。测试清理仅允许以 `_test` 结尾的数据库，不能清理应用库。

微信 AppID/Secret 由用户申请并在本机配置；微信真机及官方登录实际验收在凭据与设备条件就绪后执行。开发模式先用已获授权的本地测试登录完成可操作联调。

## 5. 推荐技术方案

沿用 Taro + React + FastAPI + MySQL，使用 `aiomysql` 连接池、参数化 SQL、独立 repository，使用 PyJWT 签发与验证 JWT。新增依赖锁定到实际验证版本，不以本次扩展为由升级现有框架或 AI 适配器。

### 后端职责与文件

| 路径 | 职责 |
| --- | --- |
| `backend/app/core/config.py` | MySQL、JWT、微信和开发登录配置；敏感值使用 SecretStr |
| `backend/app/core/db.py` | 连接池、事务、连接超时及资源释放 |
| `backend/app/core/auth.py` | JWT、必需/可选鉴权依赖，固定算法及过期校验 |
| `backend/app/models/user.py` | 登录、资料更新、统计及历史响应契约 |
| `backend/app/services/wechat.py` | 服务端 code2Session；处理无效 code、限流、超时及畸形响应 |
| `backend/app/services/user.py` | 自动注册、资料、统计、历史及开发测试身份 |
| `backend/app/services/history.py` | 题库归属、保存完整结果、历史详情和幂等结算 |
| `backend/app/repositories/` | 用户及学习记录 SQL；按 user_id 约束访问 |
| `backend/app/routes/user.py` | 登录、用户资料、历史接口及条件启用的本地测试登录 |
| `backend/app/routes/api.py` | 保持现有出题/报告协议，接入可选用户上下文和记录服务 |
| `backend/app/main.py` | 注入依赖、生命周期、CORS 支持 Authorization 和 PUT |
| `backend/sql/001_user_system.sql` | 四张表、唯一键、关联与查询索引 |
| `backend/scripts/` | 本地环境/初始化/验收入口，敏感配置不写入版本库 |

四张表仍是 users、quiz_sessions、answer_records、reports。补足如下必要约束：openid 唯一；quiz_id 唯一；每个关卡只结算一份作答和报告；所有记录包含用户归属；最近历史使用用户与时间索引。字段长度兼容现有已允许的业务数据，不静默截断题库内容。

出题：保留现有生成服务 → 登录用户保存题库 → 返回原有 Quiz。无有效登录态按游客链路执行，不触发数据库写入。

报告：登录用户先检查归属和服务端存储的原题 → 复用原计分/报告服务 → 在同一事务中保存作答、报告和 XP；重复请求返回已保存结果，并发也只结算一次。调用 AI 期间不持有数据库行锁。无权访问或未知的账号题库明确返回错误，不拿其他用户或伪造客户端题目计入账号。

登录态有效但数据库故障时返回可重试的保存失败，不把未落库结果假报为云端保存成功。游客不依赖数据库可用性；数据库暂时不可用不应阻止游客服务启动。

新增接口：

- `POST /api/v1/user/login`
- `GET /api/v1/user/profile`
- `PUT /api/v1/user/profile`
- `GET /api/v1/user/quizzes?page=1&page_size=10`，支持服务端查询/状态筛选，避免只搜索第一页。
- `GET /api/v1/user/quizzes/{quiz_id}`
- 仅本地开发启用的 `POST /api/v1/user/dev-login`，关闭时不可使用。

所有接口沿用 `code/message/data` 响应。除登录入口外，用户接口要求有效身份；现有两个核心接口仍为可选鉴权。头像 URL 更新遵循原文档的后端接口范围；不另建文件上传系统。

- [FastAPI HTTPBearer](https://fastapi.tiangolo.com/reference/security/#fastapi.security.HTTPBearer)：`auto_error=False` 用于可选鉴权；用户资源另用必需身份依赖。
- [PyJWT 用法](https://github.com/jpadilla/pyjwt/blob/master/docs/usage.rst)：固定允许算法，显式要求必要 claim 并验证过期。
- [aiomysql 连接池](https://aiomysql.readthedocs.io/en/stable/pool.html)：正确 acquire/release、close/wait_closed，并管理事务结束。
- [MySQL 8.4 Windows 手动配置](https://dev.mysql.com/doc/refman/8.4/en/windows-install-archive.html)：官方 ZIP 的本机配置、初始化及启动路径。
- [MySQL 8.4 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)：配合唯一键与短事务控制并发结算。

确认后，按实际使用的 API 继续核查 Taro 页面生命周期、昵称输入及 FastAPI 生命周期/测试等细节，不依靠旧方案中的示例直接编码。
